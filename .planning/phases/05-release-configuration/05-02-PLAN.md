### CONTEXT: Decisions Implemented

| Decision | How this plan implements |
|----------|-------------------------|
| D-01 | Single workflow with conditional jobs: `test` job runs on push+PR; `release` job runs only on tag push (`startsWith(github.ref, 'refs/tags/v')`) |
| D-02 | Release trigger: `tags: ['v*']` on push. Job condition: `github.event_name == 'push' && startsWith(github.ref, 'refs/tags/v')` |
| D-03 | Flutter cache via `subosito/flutter-action@v2` with `cache: true`. Gradle cache via `actions/setup-java@v4` with `cache: gradle`. Go module cache via `actions/setup-go@v5` with `cache: true`. Go build output cached explicitly via `actions/cache@v4` keyed on `go.sum` hash. |
| D-04 | Go toolchain via `actions/setup-go@v5` with `go-version: '1.24'`. NDK via `nttld/setup-ndk@v1` with `ndk-version: r28`. `build_android.sh` invoked with `ANDROID_NDK_HOME` from setup-ndk output. |
| D-07 | Workflow triggers on `branches: [main]` for push and PR — no release branches. Tags are the only release mechanism. |

<objective>
**What:** Create a single GitHub Actions CI/CD workflow at `.github/workflows/ci.yml` that runs tests on every push/PR to main, and builds signed release APK+AAB on version tag pushes.

**Purpose:** Automate build verification (flutter analyze + unit tests) for every code change, and provide a one-command release mechanism (git tag + push). Eliminates manual build steps for release.

**Output:**
- `.github/workflows/ci.yml` — complete CI/CD workflow definition

**Key design decisions (D-01 through D-04, D-07 from CONTEXT.md):**
- Single workflow file with two jobs: `test` (conditional on push/PR) and `release` (conditional on tag push)
- Full CI caching strategy for sub-3-minute warm builds
- Go FFI shared library built from source in CI via `build_android.sh`
- Keystore decoded from base64 GitHub secret
- Signed APK for direct install + AAB for Play Store upload, both uploaded as artifacts
- Integration tests NOT run in CI (they require an Android device/emulator)
</objective>

      1. `actions/checkout@v4`

      4. Setup Go 1.24 with module cache (`actions/setup-go@v5`, `cache: true`, `cache-dependency-path: go_superflix/go.sum`)

      12. Build release AAB: `flutter build appbundle --release`

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| GitHub Actions runner → secrets | Secrets are injected as environment variables at runtime. Must not be leaked in workflow logs or artifact metadata. |
| CI runner → Go module downloads | Go modules downloaded from proxy.golang.org during build. Pinned versions in go.sum provide integrity verification. |
| CI runner → built APK/AAB | Signed artifacts contain the keystore signature. Artifact is stored on GitHub for 90 days. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-05-07 | Information Disclosure | Secrets leaked in CI logs | mitigate | GitHub Secrets are automatically masked in workflow logs. The `Create key.properties` step uses `${{ secrets.* }}` interpolation which GitHub redacts. Never `echo` the contents of secrets or key.properties. Use `run: cat > android/key.properties <<EOF` heredoc (no stdout). |
| T-05-08 | Information Disclosure | Keystore leaked via artifact download | accept | Artifacts have 90-day retention. Any user with read access to the repo can download artifacts. Risk accepted for single-developer project. Play App Signing provides recovery if upload key is compromised. |
| T-05-09 | Tampering | Go modules fetched in CI | mitigate | `actions/setup-go@v5` with `cache: true` and `cache-dependency-path: go_superflix/go.sum` uses checksum verification. All Go dependencies are pinned in `go.mod`/`go.sum` — CI validates integrity via Go's built-in checksum database (sum.golang.org). |
| T-05-10 | Tampering | Action versions not pinned | mitigate | All action references use pinned major versions (`@v4`, `@v5`, `@v2`, `@v1`). This ensures deterministic behavior while allowing patch updates. For stricter pinning, use full SHA references — but major version pinning is standard practice for single-developer CI. |
| T-05-11 | Spoofing | Release tag doesn't match pubspec version | mitigate | Documented in release checklist (Plan 03) as a manual verification step. CI does NOT auto-validate version tag matching pubspec.yaml — this is a known gap flagged for improvement. |

**ASVS L1 notes:** No user data processed in CI pipeline. Signing key management follows industry best practices (keystore in secrets, base64-encoded, gitignored). ASVS V6 (Cryptography) requirements met by using RSA 2048-bit key via `keytool -genkey -keyalg RSA -keysize 2048`.
</threat_model>
